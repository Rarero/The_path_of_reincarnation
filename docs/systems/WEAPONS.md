# 무기 시스템 (WEAPONS)

최종 수정: 2026-08-06
상태: 1차 확정 (D8, docs/DECISIONS.md 2026-08-06 참고)
관련 문서: docs/GDD.md 5장과 7장, docs/systems/BOONS.md 4장과 9장, docs/PROTOTYPE.md 3장, docs/WORK_PLAN_M2.md 2.4절
이 문서는 이 프로젝트의 첫 무기 설계 세션(D8) 산출물이다. RELICS.md, BOONS.md와 같은 층위의 systems 문서로 둔다. 코드는 이 세션에서 건드리지 않는다. 구현은 G4(무기 리팩터링과 환도), 아트는 A6(플레이어 검 모션과 환도)가 맡는다.

## 0. 수치 표기 원칙

이 문서의 전투 수치는 전부 초안이며 M2 밸런싱과 Windows 플레이 체감 검증에서 조정한다. BOONS/RELICS처럼 소/중/대 상대 표기를 쓰지 않고 절대 수치를 먼저 제시하는 이유는, G4가 이 문서를 바로 리소스 값으로 옮길 수 있는 기준점이 필요하기 때문이다. 기준 프레임레이트는 60fps로 잡는다(act1/ENEMIES.md의 프레임 표기와 통일).

## 1. 배경과 전제

2026-08-05 사용자 지시로 아래가 확정됐다. 이 문서는 이를 전제로 설계한다.

- 시작 무기는 검(환도)이다. 저승 초입 접수청에서 차사가 첫 대화 끝에 지급한다. 총은 시작 무기에서 빠진다
- 검은 3연타다. 점프 공격은 다른 모션이고 1회 공격이다
- 원거리 공격을 패링할 수 있다. 날아오는 타이밍에 검을 휘두르면 성립한다. 성공 효과는 무효화만이고 반사는 없다. 검에 이펙트를 얹어 성공을 확실히 알린다
- 총의 진입로는 셋이다: 런 중 드랍과 상점, 무기 교체대 해금, 대장장이 해금. 대장장이 해금 후에는 허브에서 시작 무기로 총을 고를 수 있다
- 플레이어의 총 자세 클립(shoot, reload, reload_run)은 버리지 않는다. 총으로 교체했을 때 그대로 쓴다

기존 확정 사실(GDD 5장, 7장): 무기는 2슬롯 자유 조합이며 근접과 원거리를 하나씩 들어도, 같은 종류 둘을 들어도 된다. 런 중 드랍과 상점에서 교체한다. 슬롯을 고정하지 않는 이유는 권능이 무기 종류에 연동되므로 무기 선택이 곧 어떤 권능이 켜지느냐의 선택이기 때문이다. 스태미나는 현재 대시만 소모하며 근접 공격의 스태미나 소모는 "추후 빌드 축 확장 후보"다(GDD 6장, PROTOTYPE 2장). 이 문서는 그 현행을 유지한다.

## 2. 2슬롯 무기 시스템 규격

### 2.1 슬롯 구성

- 슬롯 2개. 각 슬롯은 근접 또는 원거리 무기 아무거나 담을 수 있다(고정 없음, GDD 7장)
- 슬롯 중 하나만 활성(장착) 상태다. 공격 입력은 활성 슬롯의 무기에만 적용된다. 비활성 슬롯의 무기는 대기 상태로 보관만 된다
- 최소 보유 보장: 두 슬롯이 동시에 비는 경우는 없다. 시작 시 슬롯 0 = 환도, 슬롯 1 = 빈칸이다. 새 무기 획득 시 두 슬롯이 이미 찬 상태에서 버리기를 선택해도 마지막 남은 한 자루는 버릴 수 없다(2.4절)

### 2.2 스위칭

- 전용 입력 액션 하나(가칭 weapon_swap, 신규 액션 필요, G4에서 바인딩)로 활성 슬롯을 전환한다. 슬롯이 1개뿐이면(빈 슬롯) 입력이 무시된다
- 전환 딜레이 0.12초: 스위칭 직후 0.12초 동안은 공격도, 재스위칭도 할 수 없다. 스위칭 애니메이션(무기를 거두고 다른 무기를 뽑는 동작)의 무결성을 위한 최소 잠금이며, BOONS 9.2의 RULE_OVERRIDE weapon_swap_cooldown 키가 가리키는 "쿨다운"과는 다른 개념이다. 기본값은 weapon_swap_cooldown = none(자원이나 재사용 대기시간 없음)을 유지하고, 이 0.12초는 그 위에 항상 붙는 애니메이션 잠금이다. 솥뚜껑처럼 이 규칙 키를 timed로 바꾸는 권능이 생기면 0.12초 위에 추가 쿨다운이 얹힌다(적용 대기 상태, BOONS 8.9)
- 스위칭 허용 상태: 대시 상태를 제외한 모든 상태에서 입력 가능하다. 근접 콤보나 점프 공격 진행 중에 스위칭하면 그 즉시 남은 판정이 취소되고 무기가 바뀐다. 이미 발생한 히트(그 프레임 이전에 명중한 것)는 유지된다. 콤보 진행 중 스위칭하면 콤보 카운터는 0으로 리셋된다
- 재장전 처리: 비활성화된 무기의 내부 타이머(재장전 잔여 시간, 콤보 창 등)는 흐르지 않고 그대로 보존된다. 총을 재장전 중에 검으로 스위칭했다가 다시 총으로 돌아오면 재장전이 멈춰 있던 지점부터 이어진다(스위칭 자체가 재장전을 취소하지 않는다)

### 2.3 무기 태그 활성 판정과의 관계

무기 태그(BOONS 4장) 판정은 "활성 슬롯의 무기"를 기준으로 한다. 상세는 4장

### 2.4 드랍과 상점 획득 흐름

- 드랍이나 상점에서 새 무기를 얻을 때 빈 슬롯이 있으면 즉시 그 슬롯에 들어가고 자동으로 활성화되지 않는다(현재 활성 슬롯은 유지, 새 무기는 대기 상태로 들어간다). 플레이어가 원하면 곧바로 스위칭해서 쓸 수 있다
- 두 슬롯이 이미 찬 상태에서 새 무기를 얻으면 획득 화면에서 두 슬롯 중 하나와 교체할지, 획득을 포기할지 고른다(BOONS 7장 신당 3칸 만석 처리와 같은 패턴). 교체를 선택하면 버려진 무기는 완전히 사라진다(인벤토리 보관 없음)
- 상점 판매 품목에 무기가 포함된다(WORK_PLAN_M2 4장 D9/G5 선행). 구매 흐름은 드랍과 동일한 슬롯 규칙을 따른다
- 사망 시 무기는 소멸한다(GDD 4장 죽음 루프, 기존 규칙 유지). 검도 예외 없이 소멸하며 다음 런은 다시 슬롯 0 = 환도, 슬롯 1 = 빈칸으로 시작한다(11장에서 대장장이 해금 이후의 예외를 다룬다)

## 3. 데이터 스키마

CONVENTIONS.md 데이터 규칙(밸런스 수치는 코드에 하드코딩하지 않고 .tres로 분리)을 따른다. 현재 WeaponRifle은 전부 @export 필드와 씬 인스턴스 오버라이드로 되어 있어 이 규칙을 어기고 있다(RelicDef, BoonDef는 이미 .tres 패턴을 쓴다). 이 세션에서 WeaponDef 리소스를 도입해 정합을 맞추기로 결정한다. 실제 .tres 파일과 스크립트 작성은 G4가 한다.

### 3.1 결정: .tres로 뺀다

- 근거: RelicDef/BoonDef 선례와 동일한 이유다. 밸런스 수치가 스크립트 export 기본값에 있으면 씬을 열지 않고는 값을 한눈에 비교할 수 없고, 무기 종류가 늘어날수록(6장 로드맵) 스크립트마다 값을 흩어 두는 비용이 커진다
- 근접 무기와 원거리 무기를 별도 클래스로 쪼개지 않고 WeaponDef 하나로 통합한다. kind 필드로 분기하며, BoonDef가 계열마다 분기 필드를 갖는 것과 같은 패턴이다
- 저장 위치: resources/weapons/ (RelicDef의 resources/relics/act1/ 관례를 따라 막별 하위 폴더는 필요해지면 추가한다)

### 3.2 WeaponDef 리소스 (초안)

```gdscript

extends Resource

enum Kind { MELEE, RANGED }
## BoonDef.WeaponTag와 같은 어휘. 근접/원거리 무기는 자기 kind와 항상 같은 값을 쓴다
enum WeaponTag { MELEE, RANGED, NONE }

@export var id: StringName = &""
@export var display_name: String = ""
@export var kind: Kind = Kind.MELEE
@export var weapon_tag: WeaponTag = WeaponTag.MELEE
@export_multiline var description: String = ""
@export var implemented: bool = false
## drop, shop, exchange_stand, blacksmith 중 어디서 얻을 수 있는지 (11장)
@export var unlock_sources: Array[StringName] = []

@export_group("근접")
## 지상 콤보 타별 수치. 환도는 3개, 총검(폐지 대상)이 남아 있던 시절은 1개였다 (8장)
@export var melee_combo: Array[MeleeHitData] = []
## 콤중 창을 넘겼을 때 그리고 정상 후딜이 끝났을 때 콤보 카운터가 0으로 돌아간다
@export var melee_jump_attack: MeleeHitData = null
## 히트박스 폭 (px). 근접 무기 정체성 축 하나 (6장)
@export var melee_reach_px: float = 0.0

@export_group("원거리")
@export var ranged_magazine_size: int = 0
@export var ranged_fire_interval: float = 0.0
@export var ranged_reload_time: float = 0.0
@export var ranged_bullet_damage: int = 0
@export var ranged_bullet_speed: float = 0.0
```

```gdscript

@export var combo_window_sec: float = 0.0
```

## 4. 무기 태그와 권능 연동

BOONS.md 4장은 이미 태그 3종(근접, 원거리, 무관)과 활성 조건을 정의했지만 코드베이스 어디서도 읽지 않는다(BoonDef.weapon_tag가 존재만 한다). BOONS.md 12장 미결정 목록 "무기 태그 불일치 처리"는 "무기 설계 세션(D8)에서 종류가 늘어난 뒤 다시 본다"고 예약했다. 이 세션이 그 시점이다.

### 4.1 판정 기준: 활성 슬롯(장착 무기) 하나

2슬롯 중 "들고 있는 무기"(활성 슬롯)를 기준으로 판정한다. "보유 중인 무기"(비활성 슬롯 포함 2슬롯 전체) 기준은 채택하지 않는다.

- 근거: BOONS 4장의 설계 의도는 "좋은 권능을 살리려고 무기 종류를 바꾸게 만든다"이다. 보유 기준(2슬롯 중 하나라도 근접이면 근접 권능 활성)을 쓰면 근접 하나 + 원거리 하나를 항상 들고만 있어도 두 태그가 동시에 상시 활성된다. 그러면 스위칭이라는 행위 자체가 권능 활성화에 아무 의미가 없어져 설계 의도가 무너진다
- 활성 슬롯 기준을 쓰면 스위칭이 곧 "어떤 권능 세트를 쓸지 고르는" 실제 선택이 된다. 이것이 2슬롯 자유 조합을 만든 원래 이유(GDD 7장)와 정확히 맞는다
- 무관(NONE) 태그는 활성 슬롯과 무관하게 항상 활성이다(서낭, 삼신 계열, BOONS 8.0)

### 4.2 태그 불일치 처리: 전면 정지를 유지한다

BOONS 규칙 18(효과 미적용, 보유는 유지, 조합 재료로 사용 가능)을 그대로 유지한다. 완화하지 않는다.

- 근거: M2 시점에 근접은 환도 1종, 원거리는 총 1종뿐이다(6장 로드맵). 완화(예: 태그 불일치 시 효과를 절반만 적용)를 도입하려면 모든 BoonEffect에 새 수치 축(불일치 배율)을 얹어야 하고, 규칙 46(공격 속도 비례 금지)이 통제하는 폭주 방지 범위도 다시 검증해야 한다. 근거 없이 복잡도만 늘리는 선택이다
- 재검토 시점을 못박는다: 근접 무기가 3종(환도, 도리깨, 장창) 이상 갖춰지는 시점. 그때는 "근접 두 종을 갈아 끼우며 근접 권능만 쓰는" 플레이가 실제로 성립하므로, 완화가 필요한지 판단할 실측 근거가 생긴다
- BOONS.md 12장의 해당 미결정 항목은 이 결정으로 해소됐다고 본다. BOONS.md 본문 갱신(미결정 목록에서 빼고 4장에 각주 추가)은 이 세션의 산출물 범위 밖이라 후속 문서 동기화 세션으로 남긴다(15장)

### 4.3 구현 연동 제안 (참고, G4 최종 결정)

- Player(또는 신설할 WeaponLoadout)가 스위칭/장착 시점마다 활성 무기의 태그를 RunState에 알린다(예: RunState.set_active_weapon_tag(tag))
- BoonLoadout.flat_bonus/mult_bonus가 각 보유 BoonDef.weapon_tag를 이 활성 태그와 대조해, NONE이 아니고 불일치하면 그 권능의 stat_effects를 합산에서 제외한다. special_effects(훅 기반)도 같은 판정을 적용한다
- 이 판정은 순수 함수로 두고 gdUnit4로 단위 테스트한다(13장)

## 5. 환도 (근접, 밸런스형)

환도는 M2 시작 무기다. 정체성은 "밸런스"다. 도리깨(범위)나 장창(리치)처럼 한 축에 치우치지 않고, 데미지와 리치와 속도가 모두 중간이다.

### 5.1 현행 총검과의 비교

현행 총검(WeaponRifle): 단발, windup 0.2 / active 0.12 / recovery 0.34(총 0.66초), 근접 중 이동 불가, 콤보 창 없음. 히트박스 32x26px. 데미지 16(고정). DPS = 16 / 0.66 ≈ 24.2

환도는 이 단순 모델을 따르지 않고 3연타 콤보를 도입한다. 근거: 검은 이제 시작 무기이자 본편 메인 후보(GDD 7장 장기 방침)이므로 총검보다 존재감이 커야 한다. 콤보는 "다른 근접 콤보 관례"(사용자 지정)를 참고한 표준형(약공격 두 번 + 마무리 강공격)이다.

### 5.2 지상 3연타

| 타 | 이름 | 데미지 | windup | active | recovery(콤보 미연결시) | 콤보 창 | 전진 | 넉백 |
|---|---|---|---|---|---|---|---|---|
| 1타 | 베기 | 10 | 0.10초 | 0.08초 | 0.18초 | 0.22초 | 6px | 없음 |
| 2타 | 반대 베기 | 10 | 0.10초 | 0.08초 | 0.18초 | 0.22초 | 6px | 없음 |
| 3타 | 마무리 내려베기 | 20 | 0.14초 | 0.10초 | 0.30초(고정) | 없음(종점) | 4px | 있음 |

- 히트박스 34x28px(초안, 총검 32x26 대비 소폭 확대). 오프셋은 A6 스프라이트에 맞춰 확정
- 콤보 진행: 각 타의 active 종료 후 콤보 창(0.22초) 안에 근접 공격을 다시 입력하면 정상 후딜을 건너뛰고 곧바로 다음 타의 windup으로 넘어간다. 창을 놓치면 콤보 카운터가 0으로 리셋되고 그 타의 정상 후딜이 그대로 진행된다
- 입력 버퍼: 콤보 창이 열리기 0.05초 전부터 눌러 둔 입력도 유효하다(점프 버퍼와 같은 원칙, player.gd의 기존 버퍼링 관례를 따른다). 프레임 단위 정확도를 요구하지 않는다
- 3타(마무리) 완료 후에는 무조건 리셋되어 다음 공격은 1타부터 시작한다. 마무리는 콤보 창이 없다(캔슬 불가, 고정 후딜)
- 3타 마무리 성격: 피해 상향(1타/2타의 2배) + 넉백 + 긴 후딜(0.30초, 1타/2타의 약 1.7배) 셋을 모두 준다. 근거: 마무리는 진입 리스크(0.60초를 들여 콤보를 완성해야 도달)와 이탈 리스크(고정 후딜 동안 무방비)를 동시에 지므로, 보상도 데미지와 포지션 제어(넉백) 양쪽에서 확실해야 콤보를 끝까지 갈 이유가 생긴다
- 이동 처리: 좌우 입력에 의한 자유 이동은 3연타 내내 잠금 유지(총검과 동일하게 State.MELEE 동안 이동 입력을 받지 않는다). 대신 타격마다 짧은 전진(6px, 마무리는 4px)을 자동으로 준다. 완전 고정(총검)과 완전 자유 이동의 중간이다. 전진은 velocity 조작이 아니라 히트박스가 적에게 닿는 신뢰성을 높이기 위한 위치 보정으로 다룬다(구르며 이동하는 회피형 이동이 아니다)
- DPS 참고치: 콤보 전체 완주(0.18+0.18+0.24+0.30=0.90초에 10+10+20=40 데미지) 시 약 44.4. 1타만 반복(캔슬 없이 개별 후딜 매번 소모, 0.36초당 10 데미지)해도 약 27.8로 총검보다 높다. 콤보를 끝까지 잇는 쪽이 명확히 유리하게 설계했다

### 5.3 스태미나

환도의 3연타, 점프 공격, 패링은 모두 스태미나를 소모하지 않는다. 스태미나는 현재 대시 전용이라는 기존 원칙(GDD 6장, PROTOTYPE 2장)을 그대로 유지한다. 근접 공격에 스태미나를 붙이는 안은 이미 "추후 빌드 축 확장 후보"로 문서화되어 있고, 이 세션에서 새로 확장하지 않는다.

### 5.4 규칙 46 준수 메모 (BOONS 4장)

환도 자체의 콤보 속도는 규칙 46 대상이 아니다(무기 기본 수치이지 권능 효과가 아니다). 다만 앞으로 환도의 명중에 반응하는 산신 계열 권능(ON_MELEE_HIT 훅)을 만들 때는 규칙을 그대로 지켜야 한다: cooldown_sec가 반드시 0보다 크고, target_key가 공격 속도(콤보 진행 속도, 타수)에 선형 비례하면 안 된다. 3연타 도입으로 초당 명중 횟수가 늘어난 만큼(총검 1.5회/초 대 환도 콤보 중 최대 약 5.6회/초, 1/0.18초) 이 제약이 더 중요해졌다는 점을 8장(권능 콘텐츠) 후속 세션에 남긴다.

### 5.5 대시 캔슬 (2026-08-07 사용자 확정)

근접 공격은 어느 구간에서든 대시로 끊을 수 있다. 예비, 타격, 후딜, 마무리 후딜까지 전부 대상이다. 대시가 나가면 진행 중인 공격은 취소된다.

발단: 플레이 중 "근접 공격에 대시 후딜레이가 있어 불편하다"는 지적. 실측하면 State.MELEE 동안 대시 입력이 전부 버려졌고, 콤보를 완주하면 0.90초 연속으로 빠져나갈 수 없었다. 총검은 0.66초 한 번이면 풀렸으므로, 개별 후딜은 짧아졌는데 체감은 더 답답해진 상태였다.

취소의 대가:

- **판정 즉시 종료.** 히트박스와 참격 이펙트를 함께 끈다. 끊고도 판정이 살아 있으면 캔슬이 대가 없는 이득만 남는다. 판정 없는 궤적이 화면에 남는 것도 정보로서 거짓이다
- **콤보 카운터 0으로 리셋.** 캔슬 뒤 다음 공격은 1타부터다. 마무리만 반복하는 이득을 막는다
- **공중 1회 제한 유지.** 점프 공격을 캔슬해도 공중 공격권은 돌아오지 않는다. 캔슬은 취소지 환불이 아니다
- **스태미나 30과 대시 후딜 0.22초.** 남용 제한은 대시 자체의 기존 비용이 맡는다. 근접에 새 자원을 붙이지 않는다(5.3절 유지)

5.2절의 "이동 입력 잠금"은 그대로다. 좌우 이동으로는 여전히 공격 중 움직일 수 없고, 빠져나가는 수단은 대시 하나다. 잠금을 유지하되 탈출구를 하나 여는 형태다.

DPS 영향: 캔슬은 콤보를 리셋하므로 최적 딜링 경로가 아니다. 5.2절의 "콤보를 끝까지 잇는 쪽이 명확히 유리하다"는 설계 의도는 유지된다.

## 6. 점프 공격

- 공중에서 1회만 나간다. 모션은 지상 3연타와 다르다(내려찍기 계열 권장, A6 인계)
- 지상 콤보와 연결하지 않는다: 점프 공격은 콤보 카운터에 들어가지 않는 독립 상태다. 착지 후 지상 공격을 하면 항상 1타부터 시작한다. 근거: 공중이라는 다른 포지셔닝에서 나온 공격이 지상 콤보 진행도와 얽히면(예: 공중 공격 직후 착지와 동시에 3타 마무리를 꽂는 조합) 판정 타이밍이 복잡해지고 버그 소지가 커진다. 독립시키는 편이 규칙이 단순하고 가르치기 쉽다
- 착지 처리: 즉시 취소하지 않고 짧은 착지 후딜(0.12초)을 남긴다. 근거: 즉시 취소하면 "점프 공격으로 지상 후딜을 완전히 생략"하는 것이 항상 최적 전략이 되어 지상 콤보의 존재 이유가 옅어진다. 후딜은 기존 착지 스쿼시 연출(player.gd _land_squash_left, 0.11초)과 자연스럽게 겹치는 길이로 잡았다
- 낙하 속도는 바꾸지 않는다: 점프 공격 중에도 기존 중력(_rise_gravity/_fall_gravity)을 그대로 따른다. 슬램형 낙하 가속은 이번 범위에 넣지 않는다. 근거: 슬램 연출은 환도의 정체성(밸런스)보다 방망이류 정체성에 더 맞고, 공중 제어를 "약화형"으로 유지한다는 기존 원칙(GDD 6장)과도 맞는다
- 수치(초안): 데미지 15(1타와 마무리의 중간), windup 0.08초, active 0.10초
- 판정 창이 이미 진행 중일 때 착지하면: 남은 active 프레임은 그대로 완료하고, 그 직후 착지 후딜(0.12초)로 전환한다(공중 판정을 중간에 끊지 않는다)
- 패링: 점프 공격의 windup+active 구간도 패링 판정에 쓰인다(7장). 지상 콤보와 규칙을 통일해 "검을 휘두르는 타이밍이 곧 패링 타이밍"이라는 하나의 규칙으로 가르친다

## 7. 패링

프로젝트에 없던 신규 시스템이다. GDD에 근거가 없다.

### 7.1 판정 창

- 별도의 패링 입력은 없다. 근접 공격 입력(attack_melee)이 곧 패링 판정을 겸한다. 사용자 지시("날아오는 타이밍에 검을 휘두르면 성립한다")를 그대로 따른 것이며 입력 액션을 늘리지 않는다는 장점도 있다
- 판정 창은 검 스윙(지상 3연타 각 타, 점프 공격)의 windup 시작부터 active 종료까지다. active 프레임만이 아니라 windup을 포함하는 이유: active만 쓰면 창이 0.08~0.10초로 지나치게 좁아 발사체 접촉 시점을 맞추기가 사실상 운에 가까워진다. windup을 포함하면 타별로 0.18~0.24초가 되어(5장 표 windup+active 합) "스윙을 준비하는 동안 도착하면 성립"하는 정도의 체감이 된다
- 판정 대상 지점(원거리 쪽): 발사체가 플레이어의 패링 판정 영역(근접 히트박스 위치 근방)에 접촉하는 순간이다. 발사 순간이나 예고 순간이 아니라 "도달했을 때"를 기준으로 삼는다
- 히트스캔형(즉시 판정) 원거리 공격은 현재 게임에 없다. 생기면 패링 대상에서 기본 제외한다(접촉 시점이라는 개념 자체가 성립하지 않는다). 도입 시 별도 설계가 필요하다는 점만 여기 남긴다

### 7.2 성공 효과

- 무효화만 한다. 반사와 카운터 창은 두지 않는다(사용자 지시)
- 성공하면 발사체는 피해 없이 즉시 소멸한다(플레이어 피격 판정으로 넘어가지 않는다)
- 이펙트 요구사항(A6 인계, 구현은 하지 않고 규격만 남긴다):
  - 발사체와 검이 접촉한 지점에서 즉발성 스파크/섬광이 터진다. 등장까지 지연이 없어야 한다(성공을 놓치지 않고 읽혀야 한다)
  - 색: 적색과 청록을 쓰지 않는다. 이 프로젝트의 색 채널 규약(적색은 생기 몰림 전용, 청록은 도깨비불과 비밀 신호 전용, DECISIONS.md 2026-08-06 신당 신비감 항목)과 충돌한다. 금빛/백색 계열 섬광을 권장한다
  - 지속: 0.1~0.15초 내외로 짧게. 다음 입력을 가리지 않아야 한다
  - 사운드(미정, GDD 10장): 있다면 타격음과 확실히 구분되는 금속성 챙 소리 계열
  - 선택: 짧은 히트스톱(기존 _hitstop 패턴, 0.03~0.05초)으로 타격감을 보태는 것을 권장하되 필수는 아니다

### 7.3 남용 통제

자원 소모가 없으면(스태미나 미부과, 5.3절) 무한히 휘두르는 것이 최적 전략이 될 위험이 있다. 이 문제를 다음 조합으로 통제한다.

- 패링 자체에 내부 쿨다운을 둔다(초안 0.5초). BOONS 규칙 46("명중당 발동 효과에는 내부 쿨다운을 둔다")과 같은 철학을 패링이라는 새 트리거에 그대로 적용한 것이다. 쿨다운은 패링이 "성공했을 때만" 소모된다. 스윙 자체(허공을 가르는 것, 적을 때리는 것)는 몇 번이든 무료다. 성공 직후 0.5초 동안은 다음 발사체가 정상적으로 피격 판정을 받는다
- 판정 창이 좁다(5.2절 콤보 타별 0.18~0.24초). 무작정 스윙을 반복해도 창 밖에서 발사체가 도착하면 그냥 피격당한다
- 스윙 자체의 기회비용이 이미 존재한다: 근접 공격 중에는 대시와 달리 무적이 없고 이동이 제한된다(5.2절). 근접 적(잡도깨비, 씨름꾼)이 섞인 교전에서 원거리 패링만 노리고 계속 휘두르면 근접 위협에 그대로 노출된다. 다만 이 항목은 원거리 적 단독 조우(등불 도깨비만 있는 방)에서는 억제력이 약하므로, 최종 통제 수단은 위 내부 쿨다운이다
- 스태미나는 붙이지 않는다(재확인). 대시 전용 자원이라는 현재 골격을 흔들지 않는 선택이다. 패링에 자원을 요구하고 싶어지면 "빌드 축 확장" 논의(GDD 6장 기존 미결정)와 함께 다시 연다

### 7.4 대상 범위

- 발사체가 존재하는 모든 원거리 공격이 패링 대상이다. 1막에서는 등불 도깨비 투척이 주 대상이다(act1/ENEMIES.md 5.2, 투척 예비 24f(0.40초), 착탄 불꽃 지대 2.0초, 0.40초마다 판정 (2026-08-08 개정. 구 표기는 폭발 6f였다), 착탄 후딜 18f(0.30초), 쿨다운 60f(1.0초. 2026-08-08 개정, lantern_throw.tres 가 기준))
- 향후 원거리 무기 계열 적(부적, 각궁, 방울, 옹기 폭탄을 든 적 등, GDD 7장)도 발사체를 쓰는 이상 기본적으로 패링 대상이다. 특정 유형만 예외로 두고 싶으면(예: 광역 판정이라 개별 발사체 개념이 없는 공격) 해당 적 설계 세션에서 명시적으로 빼야 한다(기본값은 "패링 가능")
- D11(적 설계 변경) 인계 사항: 패링이 실전에서 가능하려면 발사체의 비행 시간(발사부터 플레이어 도달까지)이 최소한 검 1타의 windup(0.10초) 이상은 되어야 한다. 그래야 예고 신호를 보고 스윙을 준비할 시간이 생긴다. 등불 도깨비의 투척 예비 24f(0.40초)는 이미 이 하한을 크게 웃돌아 여유가 있다. 다만 근접 교전 거리(발사체 비행 시간이 짧아지는 상황)에서는 예비 시간과 판정 창의 합이 물리적으로 좁아지므로, D11에서 사거리별 비행 시간을 확정할 때 평균 교전 거리 기준으로 이 하한을 다시 확인해야 한다

### 7.5 근접 공격은 패링 대상이 아니다

명시한다: 패링은 원거리 공격 전용이며 근접 공격에는 적용하지 않는다.

- 근거: 씨름꾼 그랩은 슈퍼아머이고 대시 회피도 불가하다(act1/ENEMIES.md, 이미 확정된 설계). 여기에 패링까지 열면 근접 위협에 대한 대응 수단이 세 개(그랩 자체는 회피 불가가 의도)로 겹쳐 개별 수단의 존재 의미가 옅어진다
- 근접 위협에 대한 대응은 이동, 대시(무적 프레임), 거리 유지로 유지한다. 패링은 원거리 견제(등불 도깨비류)에 대한 전용 대응 수단으로 역할을 분리한다

## 8. 총 (원거리) 규격 유지와 변경점

### 8.1 유지하는 것

- 자세 클립 shoot, reload, reload_run은 그대로 쓴다(사용자 지시). 총으로 스위칭했을 때 기존 애니메이션을 재사용한다
- 탄창, 재장전(자동 재장전 + 수동 선장전), 재장전 중 이동(감속) 등 PROTOTYPE.md 3장의 원거리 규격은 그대로 유지한다. 이 문서는 원거리 파트를 다시 설계하지 않는다

### 8.2 변경하는 것: 총검(근접) 겸용을 폐지한다

현재 WeaponRifle은 사격과 근접(총검)을 한 무기 안에 함께 갖고 있다(PROTOTYPE.md 3장의 M1 검증 설계). 이 겸용을 폐지한다.

- 결정: 원거리 무기(총) 슬롯이 활성일 때 근접 공격 입력(attack_melee)은 무시한다. 근접을 하려면 스위칭으로 환도(또는 향후 다른 근접 무기)를 활성화해야 한다. 마찬가지로 근접 무기가 활성일 때 원거리 공격 입력(attack_ranged)과 재장전 입력은 무시한다
- 근거: 사용자 지시가 총 자세 클립 중 shoot/reload/reload_run만 보존 대상으로 명시하고 총검 클립은 언급하지 않았다. 검이 근접을 전담하고(원거리 공격 패링까지 검이 담당) 총은 원거리만 전담하는 구조가, "무기 선택이 곧 어떤 행동을 할 수 있는지의 선택"이라는 2슬롯 설계 의도(GDD 7장)와 정확히 맞는다. 총이 근접까지 겸하면 총 하나만 들고도 전천후가 되어 스위칭의 의미가 옅어진다
- 영향: WeaponRifle의 melee_windup/melee_recovery, MeleeHitbox 관련 export와 노드는 G4에서 정리 대상이다(제거 또는 미사용 처리는 G4가 판단). player_frames.tres의 기존 melee 클립은 총검용이 아니라 환도 3연타/점프 공격용 클립 세트로 대체된다(A6 담당)

## 9. HUD 표시 계약

현재 HUD(scenes/ui/hud.gd)는 텍스트 라벨 중심의 개발용 표시다(TextureProgressBar 2개 + Label 6개). 아이콘 기반 UI가 아니므로 이 계약도 같은 수준(텍스트)에서 일반화한다. 아이콘/그래픽 HUD로 승격하는 것은 이번 범위가 아니다.

- GameEvents.player_ammo_changed(current, magazine_size, reloading)는 유지하되 발행 조건을 "활성 무기가 원거리일 때"로 한정한다
- 신규 시그널 GameEvents.player_weapon_changed(slot_index: int, weapon_id: StringName, display_name: String, tag: int): 슬롯 구성이나 활성 슬롯이 바뀔 때마다 발행한다
- 신규 시그널 GameEvents.player_melee_combo_changed(hit_index: int, window_open: bool)(권장, 필수 아님): 콤보 진행 표시용. hit_index 0은 콤보 없음/리셋을 뜻한다. G4가 일정이 빠듯하면 생략해도 되지만, 생략 시 근접 무기 활성 중에는 콤보 상태를 알 길이 없다는 점을 감안한다
- 탄약 없는 근접 무기의 표시 규격: 활성 무기가 근접(tag=MELEE)이면 기존 ammo_label 자리에 숫자 게이지 대신 무기 이름 텍스트를 표시한다(예: "환도"). 콤보 진행 중에는 "환도 2/3"처럼 hit_index를 덧붙인다. 활성 무기가 원거리(tag=RANGED)면 기존 그대로 "%d / %d(재장전)" 형식을 쓴다
- 2슬롯 요약: 별도 라벨(신규 weapon_label)에 "주 무기 / 보조 무기" 형식으로 상시 표시한다(예: "환도 | 보조: 총"). 보조 슬롯이 비어 있으면 "보조: 없음"

## 11. 시작 무기와 총 진입로

### 11.1 시작 무기

- 슬롯 0 = 환도, 슬롯 1 = 빈칸으로 런을 시작한다(2.1절). 대장장이 해금 이후에는 예외가 생긴다(11.3절)
- 지급 흐름은 D12(시작 흐름과 허브 대화) 담당이다. 이 문서는 지급되는 무기의 규격(5~7장)만 정의한다

### 11.2 총의 세 진입로

| 진입로 | 성격 | 시점 |
|---|---|---|
| 런 중 드랍과 상점 | 그 런 한정. 2.4절 슬롯 규칙을 따른다 | 매 런 |
| 무기 교체대 해금 | 영구. 보조 슬롯(슬롯 1)을 해금된 무기 중에서 미리 채운 채로 런을 시작할 수 있게 한다 | 1회 해금 후 영구 |
| 대장장이 해금 | 영구. 기본 슬롯(슬롯 0)까지 자유화하고 강화(스탯 개선)를 제공한다 | 1회 해금 후 영구 |

### 11.3 무기 교체대와 대장장이의 역할 구분

두 시설은 순차 의존 관계로 둔다. 상세 해금 조건(무엇을 하면 풀리는지)은 D10이 다룬다. 여기서는 각 시설이 "무엇을 할 수 있게 해 주는지"만 정의한다.

- 무기 교체대(선행): 허브 마당에 자리 잡는 서비스 슬롯(GDD 8장에 이미 있는 개념)이다. 해금되면 그동안 런에서 만난(드랍이나 상점으로 획득한 적이 있는) 무기 중에서 보조 슬롯(슬롯 1) 하나를 미리 채운 채로 다음 런을 시작할 수 있다. 기본 슬롯(슬롯 0)은 여전히 환도로 고정이다
- 대장장이(후속): 해금형 NPC(GDD 8장, 1막 구출 이벤트로 허브 합류)다. 무기 해금(신규 무기 종류를 소지 가능 목록에 등록)과 강화(스탯 개선)를 전담한다. 대장장이를 해금하면 기본 슬롯(슬롯 0)까지 자유화되어, 허브에서 시작 무기 자체를 검에서 총으로(또는 향후 다른 무기로) 바꿀 수 있다(사용자 지시 그대로)
- 역할 구분 요약: 무기 교체대는 "이미 해금된 무기 중 이번 런의 구성을 정하는 창구"이고, 대장장이는 "무기 종류 자체의 해금과 강화를 담당하는 콘텐츠 게이트"다. 무기 교체대만 해금된 상태에서는 슬롯 1만 자유롭고, 대장장이까지 해금되면 슬롯 0도 자유로워진다는 점진적 진행 곡선을 의도했다
- 이 순차 관계(교체대가 먼저, 대장장이가 나중)는 이 세션의 제안이다. D10에서 실제 해금 조건을 설계하며 순서가 뒤바뀔 근거가 나오면(예: 대장장이 구출이 더 이른 이벤트라면) D10이 최종 결정한다

### 11.4 후속 세션 인계

- D10(해금과 메타 프로그레션): 무기 교체대와 대장장이 각각의 구체적 해금 조건, GameState 해금 키 설계
- D12(시작 흐름과 허브 대화): 차사의 검 지급 대사와 타이밍
- G4(무기 리팩터링과 환도): 3장 스키마, 5~9장 수치를 실제 리소스와 스크립트로 구현
- G7(해금과 허브 서비스): 무기 교체대, 대장장이 UI와 GameState 영속화

## 12. 구현 아키텍처 제안 (참고, G4 최종 결정)

설계 문서이지만 WORK_PLAN_M2가 G4의 범위로 "무기 씬 분리, 베이스 클래스 도입"을 이미 못박아 두었으므로, 후속 세션이 참고할 수 있게 방향만 남긴다. 구속력은 없다.

- WeaponBase(Node2D 공통 인터페이스): equip(), unequip(), set_facing(direction), try_primary_attack() 정도의 최소 계약. Player는 이 인터페이스로만 무기와 통신한다(call down, signal up 원칙 유지, CONVENTIONS.md)
- WeaponMelee extends WeaponBase: WeaponDef.melee_combo와 melee_jump_attack을 읽어 콤보 상태 머신(5, 6장)과 패링 판정(7장)을 처리한다. 환도 하나로 시작하지만 도리깨, 장창(10장)도 이 클래스를 재사용한다
- WeaponRanged extends WeaponBase: 기존 WeaponRifle 로직(사격, 탄창, 재장전)에서 근접(총검) 부분만 들어낸 버전이다
- Player는 두 슬롯을 WeaponBase 참조 2개(또는 신설할 WeaponLoadout 컴포넌트가 보관)로 들고, 활성 인덱스만 바꿔 스위칭한다. Health/Stamina와 같은 컴포넌트 패턴을 따른다
- 패링 판정: Projectile에 parryable: bool = true(패링 대상 원거리 공격의 기본값) 필드를 추가한다. Projectile이 플레이어 Hurtbox와 접촉하기 직전, parryable이 true이고 플레이어가 패링 판정 창 안에 있으면(예: player.is_parry_window_active() 질의) receive_hit을 부르지 않고 즉시 소멸 + 패링 성공 처리(7.2, 7.3절)로 분기한다. 판정 창 밖이면 기존 경로(hurtbox.receive_hit)를 그대로 탄다

## 13. gdUnit4 테스트 규칙 (초안)

BOONS.md 10장, RELICS.md 관례를 따른다. 실제 테스트는 G4가 tests/unit/에 작성한다.

1. 슬롯 상한: 무기 보유가 2개를 넘지 않는다
2. 최소 보유: 두 슬롯이 동시에 빈 상태가 성립하지 않는다
3. 활성 단일성: 활성 슬롯 인덱스가 항상 정확히 하나다
4. 스위칭 잠금: 전환 딜레이(0.12초) 동안 공격 입력과 재스위칭 입력이 무시된다
5. 콤보 진행: 콤보 창 안의 입력이 다음 타로 이어지고, 창 밖의 입력은 콤보 카운터를 0으로 되돌린다
6. 콤보 상한: 3타 완료 후 콤보 카운터가 자동으로 0이 된다
7. 마무리 고정: 3타는 콤보 창이 0이라 어떤 입력으로도 이어지지 않는다
8. 점프 공격 격리: 점프 공격이 지상 콤보 카운터에 영향을 주지 않는다
9. 공중 1회 제한: 착지 전까지 점프 공격이 한 번만 허용된다
10. 태그 판정 기준: 비활성 슬롯의 무기 종류가 무기 태그 활성 판정에 영향을 주지 않는다(4.1절)
11. 태그 불일치: 활성 무기 태그와 불일치하는 권능의 stat_effects와 special_effects가 합산에서 제외된다(4.2절, BOONS 규칙 18)
12. 패링 성공: 패링 판정 창 안에서 parryable 발사체와 접촉하면 피해가 0이고 발사체가 소멸한다
13. 패링 쿨다운: 패링 성공 직후 내부 쿨다운(0.5초) 동안은 다음 발사체가 정상 피해를 준다
14. 패링 범위: 근접 공격 판정에는 패링 로직이 관여하지 않는다(7.5절)
15. 겸용 폐지: 원거리 무기 활성 중 근접 입력이, 근접 무기 활성 중 원거리/재장전 입력이 무시된다(8.2절)
16. 상태 보존: 비활성 슬롯의 재장전 잔여 시간이 스위칭 동안 흐르지 않고 보존된다

## 14. 미결정 사항

- 무기 교체대와 대장장이의 실제 해금 조건과 선후 관계 최종 확정(D10 담당, 11.3절 제안은 가안)
- WeaponDef.tres 실제 파일 배치(막별 하위 폴더 필요 여부)는 무기 종류가 늘어난 뒤 판단
- 점프 공격의 정확한 모션 방향(내려찍기 vs 찌르기)은 A6 아트 세션에서 스프라이트와 함께 확정
