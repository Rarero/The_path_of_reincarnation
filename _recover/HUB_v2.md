# 시작 허브 설계: 저승 초입 접수청 (DESIGN_HUB)

최종 수정: 2026-08-06
상태: 4장과 5장 확정 (D12, docs/DECISIONS.md 2026-08-06 항목). 나머지 장은 초안 (2026-08-03 프론트엔드 확정)
연동: docs/GDD.md 4장(핵심 루프), 8장(허브와 NPC), docs/DESIGN_INTRO.md, docs/systems/WEAPONS.md 11장, docs/ART_STYLE.md

## 1. 컨셉과 톤

저승 초입 접수청. 새로 죽은 혼이 가장 먼저 도착해 명부 대조를 받는 접수 청사이며, 처리 못한 혼을 쌓아두는 특수창고를 부속으로 둔다.

- 정체성: 회귀 지점이자 준비 공간. 런 시작과 사망 반송이 모두 여기서 일어난다
- 톤: 황혼빛 낡은 관청. 창구, 번호표, 서류 더미, 먼지 쌓인 선반. 3막 현대식 관료 지옥의 초기 원형으로 관료 톤 복선을 깐다
- 대비: 1막 도깨비 시장(활기찬 밤시장)과 달리 접수청은 정적이고 사무적이다. 팔레트도 시장의 등불 난색과 구분되게 침침한 중채도로 간다
- 확장: 초기에는 접수청 직원 소수만 있고, 해금이 쌓이며 인파와 서비스가 붐빈다(복작복작)

## 2. 서사적 위치

- 지리: 시작 허브(접수청) 다음이 1막 도깨비 시장(연옥)이다. 2막에서 삼도천을 건너 저승으로 넘어가고, 3막이 진짜 저승이다 (GDD 3장)
- 오프닝 연결: 오프닝 마지막(직접 상행 결의) 직후 이 접수청에서 플레이가 시작된다. 오프닝의 저승사자가 허브 NPC "실수한 차사"와 동일 인물이다 (docs/DESIGN_INTRO.md)
- 오프닝 대사의 연속 (2026-08-06 D12): 오프닝 7페이지에서 차사의 말이 "거긴 함부로 가는 데가—"로 끊긴다. 허브 진입 직후의 첫 대화가 그 문장을 잇는다. 컷신 없이 오프닝과 허브를 잇는 장치이며 첫 런 게이팅의 서사적 근거이기도 하다(5.3, 5.7절)
- 접수 관원의 서사 위치: 오프닝 6페이지의 300년 대기줄과 50년 특수창고 창구가 이 관원의 창구다. 관원이 지도를 주면서 접수 기록을 남기지 않는 것은 정식 접수를 하면 그 대기줄에 서야 하기 때문이다
- 죽음 반송: 런 중 소멸하면 접수청으로 반송된다. 명부에 없는 미결 건이라 소멸하지 못하고 특수창고로 재입고되는 형식이다 (GDD 4장 죽음 루프)

## 3. 공간 구성 (기준 해상도 480x270, 가로 진행)

허브는 좌우로 걸어다니는 2D 공간이다. 좌측이 특수창고(사적 공간), 우측이 상행문(1막 진입)이다.

- 좌측: 특수창고. 주인공이 재입고되는 곳. 사망 반송 스폰 지점을 여기 둔다. 실수한 차사가 스폰 지점 바로 옆에 있다
- 중앙: 접수 홀. 민원창구와 대기줄. 접수청 직원 NPC가 자리한다
- 우측 창구: 상행문 바로 앞의 민원창구. 접수 관원이 여기 있다 (5.5절)
- 우측 끝: 상행문. 위로 뻗은 길과 1막 진입구. 상호작용으로 런 시작
- 지면: 평평한 바닥 한 층에서 시작한다. 발판 기믹은 두지 않는다(허브는 플랫포밍 공간이 아니다)
- 동선 원칙 (2026-08-06 D12): 스폰(좌) → 차사 → 접수 관원 → 상행문(우)이 한 방향 편도로 이어진다. 첫 런 게이팅 두 조건(5.3절)이 모두 이 편도 동선 위에 있어 되돌아가는 이동이 생기지 않는다

해상도 표기 정정 (2026-08-06): 이 장은 320x180으로 적혀 있었으나 논리 해상도는 2026-08-04 결정으로 480x270이다(project.godot viewport 480x270, 창 1440x810). 5장의 UI 좌표는 480x270 기준이다. hub.gd의 카메라 한계 상수(CAMERA_TOP -8, CAMERA_BOTTOM 180)가 320x180 시절 값으로 남아 있으므로 구현 세션이 확인한다.

- 캐릭터 아트 (2026-08-03 PixelLab 생성): 실수한 차사(저승사자, 검은 갓과 검은 두루마기)와 접수 관원(청회색 과로 관원)을 생성해 art_src/generated/pixellab/frontend/에 정리했다. 붉은 관복 판관 계열은 3막용, 감재사자도 기반 화려 저승사자는 보류다. 톤앤매너는 관원 프레임을 스타일 레퍼런스로 통일했다. 상세는 docs/DECISIONS.md와 인박스 README

- 대사 해금 방침 (2026-08-06 D12 구체화): GDD 2장 전달 방식의 "허브 NPC 단편 대화(런을 반복할수록 새 대사 해금)"를 허브 쪽 규격으로 옮긴 것이다. 상시 순환 대사에 진행도 해금 대사와 사건 반응 대사를 얹는 3계층이며, 규격과 대사 원문은 5.6절과 5.7절에 있다. 차사에 먼저 적용하고 다른 NPC는 각자의 구현 세션에서 같은 구조를 재사용한다
- 접수 관원 아트 (2026-08-06): PixelLab 생성분이 art_src에 있으나 애니메이션 세트는 A9(허브 NPC 잔여) 몫이다. G12는 다른 미배치 NPC와 같은 플레이스홀더(ColorRect + Label)로 배치하고 NpcActor를 붙여 둔다. "정적 단일 프레임 배치 금지" 규칙은 아트가 붙은 NPC에 적용되며 플레이스홀더 단계는 예외다
- 피격 판정 없음 (2026-08-06 D12): 허브 NPC와 배경 군상은 Hurtbox를 갖지 않는다. 허브에서 전투 입력이 허용되므로(7장) 명시해 둔다

## 5. 상호작용과 시작 흐름

5.1은 기존 규칙에 설명을 보탠 것이고, 5.2부터 5.7까지는 2026-08-06 D12에서 확정했다. 구현은 G12(허브 시작 흐름)가 맡는다.

### 5.1 상호작용 방식

- 방식: 대상 근처에서 위(move_up)를 누르면 상호작용한다. 별도 입력 액션을 신설하지 않고 기존 move_up을 재사용한다
- 범위: hub.gd의 INTERACT_RANGE 30px. NPC 간격은 이보다 넓게 두어 프롬프트가 겹치지 않게 한다
- 프롬프트: 플레이어가 상호작용 범위에 들어온 대상 위에 안내 라벨을 띄운다(예: "위: 대화")
- 토스트: 대화가 아닌 짧은 안내는 화면 상단 라벨에 2.5초 띄운다(hub.gd의 기존 MessageLabel). 게이팅 잠김 안내가 이 경로를 쓴다
- 상행문(1막 진입): 위를 누르면 페이드 후 런으로 전환한다 (SceneRouter.goto_run). 첫 런은 5.3절 조건을 먼저 만족해야 한다

### 5.2 대화 시스템 규격

한 줄 토스트로는 3단계 대화를 담을 수 없으므로 순차 대화 상자를 신설한다. 다른 NPC의 기존 스텁 메시지도 이 시스템으로 흡수한다.

**데이터 구조.** 대사 한 줄은 사전이고, 대화 하나는 그 배열이다. DESIGN_INTRO 5장 선례를 따라 M2 단계는 스크립트 상수로 두고 콘텐츠가 커지면 .tres로 이관한다. 대사가 15줄을 넘으므로 hub.gd에 두지 않고 별도 스크립트(예: scripts/npc/hub_lines.gd)에 모은다.

```
대사 한 줄: { "speaker": String, "text": String, "effect": StringName }
대화 하나:  { "id": StringName, "lines": Array, "skippable": bool, "on_finish": StringName }
```

- effect: 그 줄이 표시되는 순간 발생하는 연출 훅. 값은 grant_sword, grant_map 두 개로 시작한다. 빈 값이면 없음
- on_finish: 대화를 끝까지 본 시점에 세울 플래그 키. 값은 chasa_intro_done, map_received (5.3절)
- speaker: 화자 표시명. 빈 문자열이면 이름표를 그리지 않는다(독백이나 시스템 안내용)

**진행 입력.** move_up 또는 ui_accept. 새 액션을 신설하지 않는다. 상호작용과 진행이 같은 키인 것은 의도한 것이며(DESIGN_INTRO 4.1 오프닝과 같은 규약), 대화 상자가 열려 있는 동안 hub.gd의 상호작용 판정은 정지하고 대화가 닫히는 프레임의 입력은 소비된 것으로 처리해 같은 대화가 곧바로 다시 열리지 않게 한다.

**표시.** 화면 하단 고정 상자다. 480x270 기준 좌표다.

| 항목 | 값 |
|---|---|
| 상자 | Rect2(48, 192, 384, 62). 판 Color(0.06, 0.06, 0.10, 0.92), 테두리 1px 먹선 |
| 화자 이름표 | 상자 안쪽 좌상단, 폰트 8px, 색 INK_DIM (0.60, 0.58, 0.54) |
| 본문 | 폰트 9px, 색 INK (0.90, 0.87, 0.80), 행간 13px, 최대 2행 자동 줄바꿈 |
| 획득 강조 줄 | 등불 호박 (0.92, 0.66, 0.28). effect가 붙은 줄에만 쓴다 |
| 다음 표식 | 상자 우하단 작은 삼각, 다음 줄이 있을 때만 깜빡인다 |

팔레트와 폰트 크기는 EventResultPopup(scenes/ui/event_result_popup.gd)과 같은 값을 쓴다. 색 채널 규약(적색은 생기 몰림 전용, 청록은 도깨비불과 비밀 신호 전용)을 지킨다.

**지속.** 자동으로 넘어가지 않는다. 한 줄은 플레이어 입력이 있을 때만 다음으로 간다. 게이팅 대화가 타이머로 흘러가면 읽기 속도 편차를 감당하지 못하고, 검 지급이 그 대화 안에 있어 반드시 끝까지 읽혀야 한다. 마지막 줄 이후에는 상자를 즉시 닫는다.

**글자 노출.** 타자 연출을 쓴다. 노출 속도 45자/초, 진행 입력 1회면 그 줄 전체를 즉시 노출하고 한 번 더 눌러야 다음 줄로 간다(2단 입력). 한 줄 전체가 처음부터 떠 있으면 넘김 입력이 대사를 건너뛴 것처럼 보인다.

**건너뛰기.** skippable이 참인 대화만 ui_cancel로 즉시 종료한다. 차사 첫 대화(게이팅)와 접수 관원 지도 지급 대화는 거짓이다. 검과 지도가 그 대화 안에서 지급되므로 건너뛰기를 허용하면 아무것도 받지 않은 상태로 나갈 수 있다는 인상을 준다. 두 대화 모두 짧아(6줄, 2줄) 부담이 없다. 그 밖의 대화는 참이다.

**중단 내성.** 대화 도중 창을 닫거나 게임을 끄면 진행이 저장되지 않고 다음 상호작용에서 처음부터 다시 시작한다. 줄 단위 진행 저장은 두지 않는다.

**분량 상한.** 대사 1개는 70자 이내(2행), 대화 1개는 6줄 이내다. 넘으면 대화를 나눈다. 대사량 최소 방침(GDD 2장, Dead Cells 상한)을 규격으로 못박은 값이다.

**플레이어 입력.** 대화 중에는 플레이어 컨트롤러 입력(이동, 점프, 대시, 공격)을 막는다. 트리 자체는 멈추지 않는다(get_tree().paused를 쓰지 않는다). NPC 유휴 애니메이션이 계속 돌아야 화면이 죽지 않기 때문이다.

### 5.3 첫 런 게이팅

**조건.** 첫 런에 한해 상행문은 두 조건을 모두 만족해야 열린다.

1. 차사 대화 완료 (chasa_intro_done)
2. 접수 관원에게 지도 수령 (map_received)

두 대상이 스폰에서 상행문까지의 편도 동선 위에 순서대로 놓여 있어(3장) 되돌아가는 이동이 없다. 두 번째 런부터는 조건 없이 열린다.

**플래그와 저장.** GameState에 아래 필드를 둔다. 이름과 타입을 고정한다.

| 필드 | 타입 | 의미 |
|---|---|---|
| chasa_intro_done | bool | 차사 3단계 대화를 끝까지 봤다. 환도 지급도 이 시점에 함께 일어난다 |
| map_received | bool | 접수 관원에게 1막 지도를 받았다 |
| run_count | int | 상행문을 나선 횟수. 상행문 통과 직전에 1 올린다 |
| chasa_lines_seen | Array[String] | 소진된 1회성 대사 id 목록 (5.6절) |

- 저장 파일: user://meta.json (신규). SaveGame의 user://run_suspend.json과 별개 파일이다. 런 중단 저장은 사망과 완주에 삭제되지만 이 플래그들은 사망 후에도 남아야 하므로 같은 파일에 둘 수 없다
- 스키마: { "version": 1, "intro_seen": bool, "chasa_intro_done": bool, "map_received": bool, "run_count": int, "chasa_lines_seen": [String] }
- intro_seen을 함께 넣는다. 같은 GameState 필드이고, 저장하지 않으면 게임을 껐다 켤 때마다 오프닝을 다시 보는 현재 결함이 남는다. 추가 비용이 없다
- 읽고 쓰는 코드는 GameState 안에 상수 1개(META_PATH)와 함수 2개(save_meta, load_meta)로만 둔다. G7(해금과 허브 서비스)이 해금 플래그와 여의주까지 이 파일로 흡수할 때 통째로 들어내기 쉬운 형태를 의도한 것이다. 쓰기 시점은 플래그가 바뀌는 순간이며(대화 완료, 지도 수령, 런 시작) 주기 저장은 하지 않는다
- 여의주 조각과 해금 4키의 영속화는 G12 범위가 아니다. G7이 같은 파일에 얹는다

**게이팅 UX.** 플레이어가 무엇을 해야 할지 모르는 상태를 만들지 않는다. 아래 다섯 가지를 겹쳐서 안내한다.

- 상행문 프롬프트를 감추지 않는다. 잠긴 동안 라벨을 "위: 상행문 (잠김)"으로 바꾼다. 프롬프트 자체를 감추면 그곳이 출구라는 사실조차 전달되지 않는다
- 상행문에서 위를 누르면 미충족 조건에 따라 토스트를 띄운다. 차사 대화 미완이면 "차사가 아직 할 말이 남았다", 지도 미수령이면 "창구에서 약도를 받아 가라". 씬 전환은 일어나지 않는다
- 조건이 남은 대상의 머리 위에 상시 표식(작은 먹색 느낌표)을 띄운다. 해당 조건이 충족되면 사라진다. 아트는 A9로 넘기고 G12는 플레이스홀더로 둔다
- 첫 런 허브 진입 직후(chasa_intro_done이 거짓일 때) 차사가 먼저 부르는 토스트를 1회 띄운다. 대사는 5.7절. 대화 상자가 아니라 토스트라 조작권을 뺏지 않으며, 스폰 직후 시선을 차사에게 준다. 오프닝 마지막이 차사의 끊긴 말이라 서사적으로도 이어진다
- 강제 이동과 카메라 팬은 쓰지 않는다. 조작권을 뺏지 않으며, 차사가 스폰 지점 바로 옆(약 50px)이라 진입 직후 이미 화면 안에 들어와 있다

**조건 순서.** 두 조건에 순서를 강제하지 않는다. 차사를 지나쳐 접수 관원에게 먼저 가면 지도를 먼저 받고, 상행문 토스트가 차사 쪽을 가리킨다. 순서를 강제하면 관원이 지도를 안 주는 반려 대사가 하나 더 필요해지고 그것도 결국 되돌아가게 만든다. 지나치기 자체는 위의 자동 호출 토스트와 차사 머리 위 표식으로 막는다.

### 5.4 환도 지급

- 시점: 차사 대화 마지막 줄(effect = grant_sword)에서 지급한다. 대화는 한 번의 상호작용에서 6줄이 연속으로 흐르며 도중에 끊어 다시 말을 걸게 하지 않는다(2026-08-06 사용자 확정). 단계를 나누면 두 번째 말 걸기를 건너뛴 플레이어에게 같은 잠김 안내를 반복하게 되고 검 없는 구간이 길어진다
- 연출: 차사가 검을 내미는 전용 클립(hand_over)은 A9 아트 몫이다. 그 전까지는 NpcActor의 스쿼시(_pop)와, 차사 위에서 플레이어 쪽으로 0.5초 이동하는 환도 아이콘 트윈으로 대체한다
- 획득 표시: EventResultPopup 규격을 재사용한다. 제목 "환도", 획득 줄 "환도(검)". 획득 표시 UI를 새로 만들지 않는다
- 실제 장착: 지급 순간 허브에서도 슬롯 0에 실제로 장착된다(2026-08-06 사용자 확정, 허브 전투 입력 전면 허용). 받은 자리에서 바로 휘둘러 보는 것이 곧 획득 피드백이 되고 허브가 조작 확인 공간이 된다
- 허브의 무기 상태 = 다음 런의 시작 구성이다. chasa_intro_done 이후에는 허브에 있는 동안 항상 슬롯 0 = 환도가 장착돼 있다. 무기 교체대(G7)가 슬롯 1을 채우면 허브에서 그 구성이 그대로 보인다
- 대화 전 상태: 무기 0자루다. 이는 WEAPONS 2.1 "두 슬롯이 동시에 비는 경우는 없다"의 유일한 예외이며 런 밖(허브)에만 성립한다. 무기가 없으면 공격 입력은 무시된다. 상행문이 잠겨 있으므로 무기 없이 런에 들어가는 경우는 구조적으로 생기지 않는다
- 두 번째 런부터: WEAPONS 2.4대로 슬롯 0 = 환도, 슬롯 1 = 빈칸으로 시작한다. 지급 플래그를 따로 두지 않고 chasa_intro_done 하나가 겸한다. 플래그를 둘로 나누면 대화는 끝났는데 검이 없는 어긋난 상태가 생길 수 있다
- 무기 지급 로직 자체는 플래그를 보지 않는다. 런 시작 구성의 기본값은 환도이고 플래그는 게이팅과 연출에만 쓴다. 대장장이 해금 이후 슬롯 0이 자유화되는 예외는 WEAPONS 11.3이 다루며 M2 범위 밖이다

### 5.5 접수 관원과 지도

- 배치: 상행문 앞 창구. 노드 이름 NpcClerk, 표시명 "접수 관원". 상행문(x=1349)에서 최소 60px 이상 떨어뜨려(INTERACT_RANGE 30px의 2배) 프롬프트가 겹치지 않게 한다. x는 1220~1260 구간에서 배경의 창구 도형에 맞춰 G12가 씬에서 확정한다
- 조형: 기존 설계 유지. 과로한 관료, 청회색 관복, 다크서클, 서류 더미
- 지도 지급의 성격: 첫 런 상행문 게이팅의 조건이다(5.3절). 대신 노드 지도 UI 자체에는 조건을 걸지 않는다. 지도는 런 진행의 필수 UI이고 이것을 잠그면 1막 안에서 진행 불능이 생길 수 있으며 G11(노드 지도 수정)에 조건 분기를 하나 더 얹게 된다. 게이팅을 허브 안(상행문)에서 끝내면 G11 범위와 분리된다
- 첫 대화: 지도 지급 2줄. skippable 거짓, on_finish = map_received
- 이후 대화: 지도 마크 읽는 법 3줄. 반복 가능, skippable 참. 선택지 UI를 만들지 않고 "다시 말을 거는 것"을 곧 설명 요청으로 본다. 선택지 분기를 넣으면 커서와 취소와 다중 분기까지 대화 시스템 규격이 커지며 M2 범위가 아니다
- 두 번째 런부터 관원 대화는 전부 선택이다

**지도 마크 설명의 형식.** 정본은 지도 화면 안의 범례다. 관원 대화는 그 범례를 어디서 보는지 알려주는 짧은 대화로 둔다.

- 근거: 설명이 필요한 시점은 허브가 아니라 지도를 실제로 보는 순간이다. 허브에서 노드 8종을 외우게 하는 것은 설계 실패다. 대사량 최소 방침도 지켜진다
- 여는 법: 지도가 열려 있는 동안 inventory(I) 입력이 범례 패널을 토글한다. 새 액션을 만들지 않는다. 지도가 떠 있는 동안 상태 창이 열리지 않는 것은 의도된 동작이므로(G11 주의사항) 그 규칙과 충돌하지 않는다. 지도 화면 하단에 상시 조작 힌트를 둔다. 관원 대사에는 키 이름을 넣지 않는다(키 바인딩이 바뀌어도 대사가 깨지지 않게)
- 설명 대상: 노드 종류 8종(전투, 이벤트, 신당, 중간보스, 상점, 내기, 쉼터, 보스)의 기호와 한 줄 뜻, 확률 등급 표식 3종(좋은 예감, 반반, 스산함)의 뜻
- 범례는 확정된 기호 집합을 그대로 읽어 그린다. 별도 그림을 하드코딩하지 않는다. 현재 아이콘이 6종이라 8종과 어긋나는 문제는 G11이 해결하며 범례는 그 결과를 따른다
- 정보 공개 범위를 넓히지 않는다. 범례는 기호의 뜻만 설명한다. 확정된 이벤트 결과는 비공개이고(EVENTS 10.1), 중간보스 개체도 비공개이며 전투 유형만 표시한다(RUN_STRUCTURE 10장)

### 5.6 이후 런의 차사 대사

게이팅이 풀린 뒤에도 차사에게 말을 걸 수 있다. 반복 피로를 막기 위해 3계층으로 나눈다.

| 계층 | 수량 (M2) | 반복 | 조건 |
|---|---|---|---|
| 상시 순환 | 4종 | 반복 | 없음. 직전에 나온 것은 연속으로 다시 나오지 않는다 |
| 진행도 해금 | 4종 | 1회성 | run_count 임계값 1, 3, 6, 10 |
| 사건 반응 | 2종 | 1회성 | 1막 보스 첫 격파, 대장장이 해금 |

- 우선순위: 사건 반응 > 진행도 해금 > 상시 순환. 위 계층에 출력 대기 중인 대사가 있으면 그것부터 낸다
- 1회성 대사는 출력 후 chasa_lines_seen에 id를 넣어 소진 처리한다(5.3절)
- 총 10종이다. 5.7절 초안은 종당 1줄이라 10줄이며 종당 2줄까지 허용한다(상한 20줄)
- 사건 반응 2종은 훅만 정의한다. 실제 사건 플래그(보스 격파 기록, 대장장이 해금)와의 연결은 D10과 G7 범위이며 G12는 플래그가 없으면 그 대사를 건너뛴다
- 접수 관원도 같은 구조를 쓰되 M2 범위는 상시 순환 2종이다

## 6. 죽음 반송과 1막 진입

- 1막 진입: 상행문 상호작용 시 SceneRouter.goto_run()으로 노드 맵 기반 런(run_stage)에 들어간다. 첫 런은 5.3절 게이팅 조건을 먼저 만족해야 한다. 통과 직전에 run_count를 1 올리고 meta.json에 쓴다
- run_count 증가 시점을 런 시작으로 잡은 이유: 사망이나 완주 시점 증가는 중단 저장 재개와 얽히고 완주 경로가 아직 닫혀 있지 않다. 완주 전까지 허브 복귀는 곧 사망이므로 허브에서 run_count가 1 이상이면 최소 한 번 죽고 돌아온 상태라는 판정이 그대로 성립한다(5.6절 진행도 해금이 쓰는 판정)
- 죽음 반송: 스테이지에서 사망 시 허브로 돌아온다. stage.gd에 return_to_hub_on_death 옵션(기본 거짓)을 추가하고, 참이면 재시작 대신 SceneRouter.goto_hub를 호출한다. stage_act1_rough에만 참으로 설정해 기존 검증 씬(stage_verify)의 재시작 동작은 보존한다
- 반송 지점: 허브 좌측 특수창고의 SpawnPoint에서 재등장한다
- 반송 후 게이팅은 다시 걸리지 않는다. chasa_intro_done과 map_received가 디스크에 남아 있어 사망해도 유지된다(5.3절)

## 7. 씬 구조 (스켈레톤)

노드 트리 개요:

- Hub (Node2D, hub.gd)
  - Background (Node2D 또는 CanvasLayer): 침침한 접수청 배경 플레이스홀더(ColorRect)
  - Terrain (Node2D): 바닥과 좌우 벽. res://scenes/levels/block.tscn 재사용(충돌 레이어 world)
  - Player (res://scenes/player/player.tscn 인스턴스): Camera2D 포함. hub.gd가 카메라 한계를 허브 폭으로 설정
  - SpawnPoint (Marker2D): 좌측 특수창고
  - Interactables (Node2D): 각 NPC와 서비스, 상행문. Node2D + ColorRect + Label 플레이스홀더
  - Crowd (Node2D): 해금 수 비례 군상 플레이스홀더
  - Ui (CanvasLayer): 상호작용 프롬프트, 안내 메시지 라벨, 대화 상자(G12 신설), 획득 팝업(EventResultPopup 재사용)

- 재사용: player.tscn과 block.tscn을 그대로 써서 충돌과 카메라가 M1과 동일하게 동작한다
- 허브 전용 입력 게이팅 (2026-08-06 확정, 사용자 지시): 두지 않는다. 허브에서 이동, 점프, 대시, 공격, 재장전 입력이 전부 살아 있다. 환도를 받은 뒤 허브에서 검을 휘두를 수 있는 것은 의도한 동작이며 받은 무기의 조작을 그 자리에서 확인하는 공간이 된다. NPC와 군상은 피격 판정이 없어 아무 일도 일어나지 않는다(4장). 유일한 예외는 대화 중이며 그동안만 플레이어 입력을 막는다(5.2절). 7장에 "후속 폴리시"로 남아 있던 항목을 이 결정으로 닫는다
- 조작 힌트 라벨(Ui/Hint)은 무기 전환 반영이 필요하다. 현재 "사격 K 근접 J 재장전 R" 표기는 총 기준이고 시작 무기가 환도로 바뀌었다. G4의 입력 규격이 확정된 뒤 G12가 맞춘다
- 디버그: 숫자키로 해금 플래그를 토글해 복작복작 확장을 눈으로 확인한다(스켈레톤 검증용). G12는 게이팅 플래그를 되돌리는 디버그 키도 함께 둔다(첫 런 흐름을 반복 검증하려면 필요하다). 기존 0번(reset_all)이 meta.json까지 지우도록 확장하는 방향이 가장 단순하다. 상세 키 배열은 M1_CHECKLIST에 준하여 정리

## 8. 아트 요구

- 접수청 배경 (art_src/requests/015): 황혼빛 관청 배경. 좌측 특수창고 선반, 중앙 민원창구와 대기줄, 우측 상행문. 레이어 분리(원경 청사, 중경 창구, 근경 지면)
- 허브 NPC 세트 (art_src/requests/016): 실수한 차사(화려한 관복), 늙은 서기 혼, 주모, 삽살개, 대장장이 도깨비. 도깨비 계열은 reference/act1_dokkaebi 고증 적용
- 군상(떠도는 혼): 배경 군상 스프라이트. 요청서 012 인파 자원과 공유 검토
- 팔레트: 시장 난색과 구분되는 접수청 서브 팔레트. M2 스타일 선별에서 추출
- D12 추가분 (A9 범위): 접수 관원 애니메이션 세트(유휴 루프와 놀람, 차사와 같은 골격), 차사의 검 건네는 클립 hand_over, 게이팅 표식 아이콘(작은 먹색 느낌표), 환도 아이콘(획득 연출용 소형)

## 9. M 의존과 후속

- M1 스켈레톤 범위: 허브 씬 흐름(오프닝 인계, 사망 반송, 1막 진입), NPC와 서비스 플레이스홀더, 해금 기반 표시, 상호작용 스텁, 디버그 토글
- G12 (허브 시작 흐름): 5장 전체를 구현한다. 대화 시스템, 차사 6줄과 환도 지급, 첫 런 게이팅과 meta.json, 접수 관원 배치와 지도 지급, 이후 런 추가 대사. 선행은 G4(무기 리팩터링과 환도)이며 검 지급이 실제 장착으로 이어지려면 무기 구조가 먼저 있어야 한다
- G11 (노드 지도 수정): 지도 마크 범례 패널을 구현한다. 여는 입력은 지도가 열린 동안의 inventory(I) 재사용, 대상은 노드 8종과 확률 등급 3종이다(5.5절). 아이콘 6종과 노드 8종의 매핑 확정이 선행이다
- G7 (해금과 허브 서비스): meta.json을 해금 4키와 여의주 조각까지 담는 체계로 확장하고 GameState의 save_meta/load_meta를 흡수한다. 무기 교체대와 대장장이 UI도 여기서 붙는다
- A9 (허브 NPC 잔여): 접수 관원 애니메이션 세트, 차사의 검 건네는 클립(hand_over), 게이팅 표식 아이콘
- 후속: 배경 아트, 상점과 영구 업그레이드 실동작, 늙은 서기 혼과 주모 배치, 사운드
- 명칭 정합(후속): DESIGN_ACT2.md와 RUN_STRUCTURE.md의 "나루" 표기가 허브가 아니라 2막 삼도천 선착장을 가리키는지 점검한다
